# USB 手柄兼容说明

## 2026-10-14 r5阶段现状

2026-10-14后续用户反馈：“我实测也是OK了”。当前这只新型号手柄的r5适配记为用户实测通过；未操作的其他样本与专项保持原验证范围。

FW-HID-004的新5接收器均为20BC:5500/bcd1003、端点64/报告描述符123、实际USB9字节；仅A/MI_01一只完成18项PC标定。10月14日同连接IF2启停实验确认辅助端点服务的必要性，r5据此增加正式辅助服务及独立DWT失效保护，已烧录并完成单只12项车端输入台架验证，**不代表物理行驶验收**。见[新设备实测](devices/20bc-5500-new9-20261013.md)、[r4及诊断历史](releases/2026-10-13-new9-gamepad.md)和[r5记录](releases/2026-10-14-gamepad-r5.md)。此前r2/r3用户反馈不代替r5或新型号验收。

| r5配置 | 选择与输入 | 控制接口和验证范围 |
|---|---|---|
| profile4，新九字节20BC | VID20BC/PID5500、bcd1003、端点64、报告描述符123；实际恰9字节，无ID | 接口0/1独立IN81/82；物理右X/Y为byte5/6，匹配时额外服务IF2/IN83；PC单只标定通过，r5单只车端输入台架验证通过 |
| profile3，八字节20BC | VID20BC/PID5500、bcd1003、端点8、报告描述符90；实际恰8字节，无ID | 接口0/1独立IN81/82，物理右X/Y为byte6/5；r2/r3有历史实物证据，r5只有软件回归 |
| profile2，0810 | VID0810/PID0001，实际8字节含Report ID1/2 | 单物理接口分成两个逻辑通道；保留数字右杆/对应面键同效的PC模式限制，r5只有软件回归 |
| profile1，旧20BC兜底分支 | 20BC未命中上述具体条件时保留旧9字节解码 | 单接口历史路径，旧物理设备未在本轮重新验收 |
| profile0，legacy | 原手柄入口与既有8～32字节布局 | 保留原算法，通用HID兼容性不由此证明 |

旧FW-HID-001接收器的历史元数据同样为bcd1003、64/123，也会命中profile4；旧profile1源码保留不代表同一旧实物仍选择profile1。当前没有能按这些字段区分物理新旧设备的证据，不宣称旧九字节实体行为不变。这里是按实测格式选择配置，没有实现通用HID描述符解析或USB Hub多接收器支持。

profile2/3/4复用互斥控制：一只先回中松键后新动作获得控制权；当前四轴/帽回中且全部原始按钮释放后放权，10ms零窗口后新中位/新动作才可接管，另一只提前推住不排队。每路仅由自己的有效报告续500ms期限，控制通道坏包/超时与USB断开清理输出。无报告超时不能检测接收器仍重复旧非零报告的射频失联，物理关机试验必须单独进行。

新九字节profile4把Usage7/8/9/10/11/12分别映射L1/R1/L2/R2/SELECT/START，其余Usage1～6/13～15不绑定动作；所有15个原始按钮仍用于判定松键，bit15填充排除。左X/Y是byte3/4，右X/Y是byte5/6；C5/C4不参与动作或连接判断。端点容量64与实际报告9分别处理；Windows零ID占位不得传入USB解析器。

r5在精确匹配的profile4上持续读取并丢弃系统IN83输入：原始配置84字节、IF2报告描述符101、端点64字节/10ms。该管道独立缓冲，不进入Game Pad解码/回调/仲裁，也不续500ms期限。辅助NAK/ERROR按轮询重试，STALL禁用服务直到重新枚举；不发送辅助接口控制请求。

USB主机每轮处理前后以原始DWT周期差检查每路有效报告期限；即使SOF停止，控制循环仍能在期限到达时失效输入。端口/连接/断开状态、HOST_CLASS或真实custom Gamepad类型失效也会立即清缓存和两路arming；恢复后仍需新中位再操作。legacy/profile1不新增周期期限。保护不修改平衡/PID/蓝牙，也不负责自动恢复异常端口；控制ISR长期阻塞和接收器重复旧非零数据仍超出该无报告期限的保证。

当前页面流程用于核对四向、回中、按键及关机；最终结果另行记录。旧型号的软件/实物回归、同对另一只及剩余4只样本按真实覆盖分别说明。成功枚举、初始三路增长和主机检查均不能代替最终车端验收。

**r3双手柄更新：** 用户在r2基本测试后要求另一只也可用。车端新八字节20BC配置现同时接收接口0/1、IN81/82，PC0810按ID1/2分流；独立管道/缓冲及接口感知请求避免互相覆盖。当前回中松键后释放控制权，10ms零窗口后需要新中位/新动作接管，持续推住不排队；每通道独立500ms期限。车端两只独立输入和核心交接数据已核实，原单只选择说明保留其r2阶段背景，当前以[双手柄记录](releases/2026-10-08-twin-dual.md)为准。

用户于2026-10-08暂停此前 `20BC:5500` 适配，其代码及下文历史说明保留。`20BC:5500` 使用接口 `0` 的专用9字节格式；其他进入现有手柄分支的设备保留legacy格式。USB枚举成功只能证明接口接入，仍须确认摇杆、方向帽和按键含义。

## 报文配置与接口选择

| 配置 | 设备和接口 | 报文约定 |
|---|---|---|
| `20BC:5500` 八字节实测配置 | bcd1003、接口0、端点8字节、报告描述符90字节共同匹配；IN81，5ms端点周期 | 无Report ID，恰8字节；左3/4、右水平6/垂直5；独立于旧九字节分支 |
| `0810:0001` 专用配置 | 固定接口 `0` / alternate `0`；HID class `3`、subclass `0`、protocol `0`；interrupt IN `0x81`，最大包8字节，2ms轮询 | 实际USB输入恰为8字节，含非零Report ID；只接受ID1，合法ID2忽略 |
| `20BC:5500` 专用配置 | 按 VID/PID 选择，固定 USB 接口号 `0`；HID class `3`、subclass `0`、protocol `0` | 无 Report ID，实际 USB 输入恰为 9 字节 |
| legacy 配置 | 保留放宽型号白名单后的手柄入口；HID class、subclass `0`、protocol `0` | 原有 8–32 字节固定布局 |

已检查的 `20BC:5500` 接收器设备版本为 `bcdDevice=0x1003`，有三个接口。其中接口 `0`、`1` 都声明 Game Pad 集合，接口 `2` 为系统/用户控制集合。本次明确使用接口 `0`，不自动切换到接口 `1`；哪个物理手柄向哪个接口发送操作仍需用户实测。证据及精确布局见 [20BC:5500 设备记录](devices/20bc-5500.md)。

`20BC:5500` 配置跳过非 Boot 流程中的 `SET_PROTOCOL` 和启动时 `GET_REPORT`，直接通过所选接口的中断 IN 端点接收。接收缓冲为 64 字节，匹配实测端点的最大包长；解析使用实际 `XferSize`，9 字节报告不会因为端点上限为 64 字节而被当成 64 字节数据。手柄数据直接交给解析器，不再借助固定帧长 FIFO 拼接或补尾。

新配置使用端点声明的 10 ms 轮询周期（下限 1 ms）；legacy 保持原有最低 50 ms。读取手柄信息时保留最新有效帧，不因一次读取后暂时没有新包而清空。

## 20BC:5500 的字段与映射

下表的字节偏移均从实际 USB 报文的 `0` 开始。Windows HID 输入缓冲会在无 Report ID 的设备数据前补一个零字节；该占位不进入 STM32 的 USB 报文，也不能据此给所有字段增加一字节偏移。[微软 HIDP_CAPS 定义](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/ns-hidpi-_hidp_caps)

| USB 字节偏移 | 已核实字段 | 固件解释 |
|---|---|---|
| `0..1` | Button Usage `1..15`，低字节在前 | 按映射表转换到原有按键位图 |
| `2` 低四位 | Hat：`0..7` 为八方向，实测中位为 `15` | 新配置方向位：UP=`1`、RIGHT=`2`、DOWN=`4`、LEFT=`8`、中位=`0`；斜向合并相邻方向，`8..15` 按 Null 处理 |
| `3`、`4` | X、Y，8 位，逻辑范围 `0..255` | 左摇杆 X、Y |
| `5`、`6` | Z、Rz，8 位，逻辑范围 `0..255` | 右摇杆 X、Y |
| `7`、`8` | Simulation Controls Usage `C5`、`C4`，8 位 | 当前不接入控制动作 |

新配置以原始值 `128` 作为摇杆中位。X 方向使用 `raw_x - 128`，Y 方向使用 `128 - raw_y`，四轴结果均限制在 `[-127, 127]`，保证原始中位得到 `0`。X/Y/Z/Rz 是描述符字段名；将它们对应到左右物理摇杆仍需复测。

按键转换表位于 `Firmware/Hiwonder/src/gamepad_report.c`。尚未逐个采集物理按键，当前采用以下待标定映射：

| USB Button Usage | 原有动作键 |
|---|---|
| `5`、`6` | L1、R1 |
| `7`、`8` | L2、R2 |
| `9`、`10` | Select、Start |
| `11`、`12` | L3、R3 |
| `1..4`、`13..15` | 不映射 |

这只是常见 DInput 编号约定，不能作为该实物按键布局已确认的证据。暂不映射其余编号，避免未经标定的按键触发现有 PID/校准操作。后续应逐键记录 USB Usage，再调整此表；不要根据外壳印字直接猜测编号。

## legacy 配置

原有 `0x2563:0x0526/0x0575` 型号白名单已取消；其他设备进入 legacy 路径后，仍须符合原报文布局。protocol `0` 本身不能证明设备就是手柄。

| USB 字节偏移 | 保留的原有解释 |
|---|---|
| `1`、`2` | 左摇杆 X、Y，保留原有中心换算和方向 |
| `3`、`4` | 右摇杆 X、Y，保留原有中心换算和方向 |
| `5` | 方向帽，低四位取反 |
| `6`、`7` | 原有按键位图，`6` 为高字节、`7` 为低字节 |
| `20`（第 21 字节） | 报文确实包含该字节时，值为 `0x02` 继续被既有状态过滤丢弃 |

legacy 解析仍接受 8–32 字节，保持原有轴、按键和 Hat 算法；没有确认其 Hat 四向位语义与新配置相同。第 21 字节的厂商定义尚未确认，不把它解释为已经验证的无线连接状态。

## 状态与验证边界

无效报文、USB断开及重新连接会清理手柄信息，控制层读取手柄数据时检查空指针。0810及新八字节20BC实测静止仍周期上报，单独启用500ms有效所选通道报告期限；0810合法ID2不会触发清零或续期。legacy与旧九字节20BC保持原有行为。本次新手柄在PC和车端的关机归中均获证据，但没有精确断电时刻，不能量化无线停车延迟或外推到全部射频失联场景。

调试器可观察 `gamepad_raw_buttons` 获取原始USB Usage位图，通过 `gamepad_reports_accepted` / `gamepad_reports_rejected` 查看解析计数，新增加 `gamepad_reports_ignored` / `gamepad_reports_timed_out` 区分另一通道与失效清零；每次重新连接时计数清零。逐键标定以原始位图为依据，不以暂定动作映射反推物理编号。

本次增加的是一个已取证型号的明确配置，没有实现通用 HID report descriptor 解析器，没有增加 XInput 或任意复合设备的通用接口选择能力。其他 `20BC:5500` 固件版本若改变报告格式，也需要重新验证。

解析器具备可在主机 GCC 下执行的 C 测试，供 GitHub Actions 验证字段、映射和长度边界；本次实际 C 测试、Keil 编译与产物结果见 [开发记录](DEVELOPMENT_LOG.md)。本次没有烧录，PC 上读取描述符和输入样本不等于 STM32 上已接收，也不等于完成整车验收。

## 最小复测步骤

固定车体并让车轮离地，保持同一主板、固件和供电条件。每只手柄使用已与其配对成功的接收器。

1. **原手柄回归。** 检查中位、左右摇杆四向、方向帽和原有按键；每次动作后回中或松开。确认 legacy 的方向、中心和动作保持原行为。
2. **20BC:5500 接口 0。** 确认新手柄操作产生接口 `0` 报告，再检查四轴中位、四向和方向帽八向。若接口 `0` 没有随操作变化，应先查接口 `1` 是否对应当前手柄，不在运行中自行切换接口。
3. **逐键标定。** 一次只按一个键，记录物理按键、USB Usage、固件动作。重点核对待确认的 Usage `5..12`；确认 `1..4/13..15` 不触发现有控制动作。
4. **状态复测。** 在有方向输入后松开，再检查 USB 拔出、重插后的控制量清理；另行记录无线关机/失联时接收器行为，不把 USB 拔出结果代替无线失联测试。
5. **保存证据。** 记录固件提交或 HEX 摘要、接收器版本、接口和各项结果。上述项目符合预期后，再单独安排落地控制验证。

若无反应或字段异常，先取得实际 VID/PID、接口/报告描述符以及中位、单轴、逐键输入的原始报文和长度，与设备记录比较。修改型号 ID 无法修正接口或报文布局差异。
