## BLE 首包故障与已确认的下行路径

v24 在 19:03 的现场日志显示成功连接 `FF:01`，选择 FFE0 服务、写类型 2，随后报告 `characteristic write failed` 并关闭会话。v24 日志没有输出数值错误码，不能将 v26 才取得的精确错误码写成 v24 直接测量结果。

v26 在 19:20 的增强日志确认：

1. GATT 连接成功，服务发现成功；本车当前提供的是 FFE0，不是资料中的默认 E0FF。
2. FFE0 下仅一个 FFE1 特征，属性 `0x18`（WRITE 与 NOTIFY）；写入和通知使用同一特征。CCCD `0x2902` 写回调状态为 0。
3. 首次发送为有响应写，`writeType=2`；仅提交了一个 11 字节帧，队列深度 0，正在等待该写回调。
4. 该写回调返回 `13/0x0D`（属性值长度无效），会话随后失败关闭。因此“蓝牙已连接”提示不能证明业务通信已经可用，也解释了本轮连接提示后界面数据没有更新的现象。

上述事实当时没有证明模块一定要求固定 20 字节。随后 v28 实施的首次幂等零指令 20 字节尾部空格探测也失败，见下文。不能通过默认忽略错误、反复重发运动/PID 设置指令来宣称恢复。

在 v24 首次连接后，MCU 的实际 RX 块已抓到：

```text
CMD|3|0|0|$
```

长度为 11 字节，接收 DWT 时间戳为 `3381998263`、RX epoch 为 1。随后快照显示 RX 读写索引均为 1，运动保护保留该实际接收时间，epoch 为 2、armed=0、speed=0、turn=0，链路错误计数均为 0。它证明至少一个零指令已从手机经所选模块抵达 MCU；不证明手机已收到遥测，不证明写完成成功，也不构成非零运动的物理失联测试。

证据：`phone-after-user-selection.txt`、`phone-v26-diagnostic-logcat.txt`（19:20:45–19:20:46）、`phone-v26-connected-no-data.txt`、`mcu/first-bluetooth-rx-block.bin`、`mcu/after-failed-gatt-link.bin`。

## PC 对照：模块信息与写入结果不一致

19:50–19:54 对同一 `HC-05D`（`FF:01`）进行独立 PC GATT 对照。业务范围限于零运动输入、电压/PID 查询及一个空格探测，没有发送非零运动指令或 PID 设置；这些查询通过 GATT 写请求发送，不能称为传输层完全无写入。独立于 Android 的对照也复现了错误 13，降低了“仅手机页面点击或 Android 缓存问题”的可能性。

## 厂商 APK 审核与 v30 适配边界

本地 `build/hcbluetooth-apk-review/` 保存了资料中实际 `HCbluetooth.apk` 的反解审核，应用包为 `com.hc.mixthebluetooth`，载荷中的 BuildConfig 标为 `1.3.0`。以下是实际 APK 代码行为的审查，不是将资料内示例源码当作运行版本，也不是厂商应用在本车上的实测结果：

- BLE 发送路径搜索 FFE1，未显式设置 write type；默认分块上限为 20 字节，尾块按实际剩余长度发送，未强制补齐。
- `onCharacteristicWrite` 只有状态 0 才正常释放发送等待并报告发送长度；非 0 仅记录状态。该分支已与 smali 核对。
- 发送等待包含超时后额外零长度写、最终跳过等处理。不能据此推导出“厂商要求无响应写”或“所有状态 13 都应当视为成功”。

具体证据在该目录 `jadx/sources/com/hc/bluetoothlibrary/bleBluetooth/BluetoothLeService.java` 与 `apktool/smali/com/hc/bluetoothlibrary/bleBluetooth/BluetoothLeService$1.smali`，以及应用 BuildConfig。这里只记录策略和来源，不将第三方反编译源码复制进维护代码。
