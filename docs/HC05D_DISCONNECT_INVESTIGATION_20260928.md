## 1. APP健康截止存在可复现的过早断开

当前 `MiniBalanLink.java` 同时使用750ms单笔写超时、CMD7实际提交后1500ms超时、上次完成健康证明后的2500ms截止。新的有效电压虽已到达，仍需等待写回调才更新旧健康时间；查询排队也会消耗整体预算。`fail()`最终主动`disconnect()`和`close()`。

直接编译实际Java并复用现有Android fake，已有回归与新增回放共529项断言通过，证据为 `build/disconnect-audit-20260928/assert_replay.py` 与 `REPORT.md`：

| 模拟时序 | 实际代码结果 |
|---|---|
| 写回调720ms、通知90ms，持续有CMD4/5 | +4410ms已收到新CMD7，但对应写回调要+5040ms到；旧整体截止+4750ms先关闭。关闭时该新电压仅340ms旧 |
| 写回调450ms、通知900ms | 查询+3700ms才实际提交，回复应+4600ms到；旧整体截止却+4400ms关闭，名义1500ms响应窗口实际只剩700ms |
| 单次写回调超过750ms，仍有遥测 | 当前实现仍按写超时关闭；这说明关闭条件不等于无线链路本身已断 |
| 同进程50次写超时→手动connect | 都能恢复，每个旧fake GATT均disconnect/close一次；旧回调被隔离。未在核心类复现永久无法手动重连 |

这是已证实的软件触发路径；没有取得11:30/11:31那一刻的APP失败原因，因此尚不能断言两次现场断开必然由该条件触发。固定450ms写回调加90ms通知的模拟也能保持在线，历史90ms/latency4不能直接换算为每包固定450ms或直接作为根因。

## 2. 手动列表存在已确认的扫描生命周期缺陷

以v36最终反解字节码为依据，实际类为 `com/Wonder/bot/dialog/SearchDeviceDialog`：

- `createDialog`先构造一次，横屏分支再构造一次并覆盖引用；两次构造都立即扫描。MainActivity固定横屏，所以正常打开列表就会走该路径。只有一个`showDialog`，不是重复显示两个弹窗。
- 取消、选中设备和点击外部关闭时，仅关闭弹窗，没有立即停止扫描。不可见的第一个实例也只能等待自己的60秒截止。
- 每次重新搜索增加一个60秒定时任务，但停止扫描未取消旧任务、也没有代次检查。旧任务可提前终止新一轮扫描，迟到结果仍可修改列表。
- `startLeScan`返回值被忽略，随后直接标记正在扫描；异步注册/频率失败没有可观察处理。Android提供扫描注册失败及扫描过于频繁等错误码，应使用现代扫描回调记录，而不能仅以旧接口返回值判定成功。[Android ScanCallback](https://developer.android.com/reference/android/bluetooth/le/ScanCallback)

对应最终smali：`SearchDeviceDialog.smali`的构造165行、工厂207/237行、取消288行、选中335/339行、扫描344行起；`SearchDeviceDialog$1.smali`38行起没有扫描代次/存活检查。代码位于本地v36构建的 `final-decoded/smali/`，反解材料不复制进Git。

这能解释重连流程退化的风险，且双扫描已获现场系统记录复核；但本机是否真正触发过扫描限流、注册失败或系统资源耗尽，还没有具体错误码。旧扫描会自然到期，不能用它单独解释任何持续时间的失败。新进程自动连接成功也会绕过该手动路径，故“杀APP恢复”不等于已证明GATT泄漏。

## 3. MCU运动超时切换可漏一次普通查询

实际生产C与原HAL适配stub编译回放，原基线及8个审查场景完成；证据为 `build/mcu-disconnect-audit-20260928/mcu_query_drop.c` 和同名log。

`bluetooth_link.c`的500ms守卫只清蓝牙运动输入并推进epoch，不直接断开无线或关闭平衡。但 `bluetooth.c`355行会丢旧epoch整块，253行也对包括CMD7在内的所有命令检查epoch和年龄；81行附近还会清掉跨epoch部分帧并重新挂接DMA。

已复现完整CMD7在499ms排队、500ms失效后才处理，或501ms完成于旧DMA，以及查询分片跨500ms时不产生回复；随后的新CMD7又正常回复。前三种丢包时`rx_errors`和`stale_frames`仍为0，`flag_move`保持1。零CMD3也会使能守卫，所以松手后的最后零帧也可能在500ms后触发一次切换；失效后并非每500ms持续清队列。

因此“MCU漏单次查询→APP健康超时主动关闭”在软件上成立。普通epoch同步不会取消已经进入TX的回复；UART错误恢复则另会abort TX，需要与普通超时区分。当前没有本次UART错误、供电跌落、复位或射频故障的直接证据。

## 下一版修复范围与验收

1. 按用户要求取消启动自动连接。下一版交付不携带 `mvtbot-debug-autoconnect.properties`，不传 `-DebugAutoConnectTarget`；手动连接仍需正常工作，不能仅取消自动路径而留下旧列表缺陷。
2. 修正健康查询的排队、接收、写回调和截止关系；新有效查询回复已到达但写回调尚在合法窗口时，不让旧截止抢先关闭。仍保留有限写超时，不无限等待或重播运动/PID命令。
3. 手动扫描使用单一owner、可取消定时器和代次；选中/关闭/后台/销毁立即停止。处理异步错误和冷却，记录实际扫描结果及连接是否发起。
4. 评估将过期运动隔离与安全查询接收分开，或对丢失的只读查询进行有界恢复；不能只豁免最末层CMD7而忽略更早的整块过滤。MCU的500ms运动保护不延长。
5. 增加本次缺失的现场指标：明确关闭原因、查询入队/提交/回包/写完成时间、等待时长、扫描代次/失败码以及GATT创建和释放结果。先以现有可复现时序做回归，再验证多次断开重连无需清理APP，以及实际运动和失联行为。

本轮产出为调查结论与下一版要求；未修改生产Java/C、替换手机APK或烧录。当前在机仍为已核验的v36，自动连接功能需在下一次更新时取消。
