# USB 手柄兼容说明

本次改动取消两处接收器型号白名单，使 VID/PID 不同、但接口和报文格式兼容的设备可以进入现有手柄处理流程。取消白名单不等于已经支持所有 USB 手柄；新手柄能否正确控制，仍需实测。

## 当前准入与报文约定

原先仅允许 `VID=0x2563`，且 `PID=0x0526` 或 `0x0575` 的设备进入手柄分支。本次在 `Firmware/Hiwonder/src/usbh_hiwonder_hid.c` 的接口初始化和设备类型识别两处取消此型号限制，保留 HID class、subclass `0`、protocol `0` 的接口条件。

`Firmware/Hiwonder/src/usbh_hid_gamepad.c` 继续按固定字节位置解码。下表使用从 `0` 开始的字节偏移：

| 字节偏移 | 现有解释 |
|---|---|
| `1`、`2` | 左摇杆 X、Y；保留原有中心值换算和方向 |
| `3`、`4` | 右摇杆 X、Y；保留原有中心值换算和方向 |
| `5` | 方向帽，保留原有低四位取反映射 |
| `6`、`7` | 按键位图，`6` 为高字节、`7` 为低字节 |
| `20`（第 21 字节） | 该字节存在时，值为 `0x02` 的报文继续被既有状态过滤丢弃 |

第 21 字节的厂商定义尚未确认，因此不把 `0x02` 解释成某种已证实的连接或配对状态。

接收和解码缓冲仍为 32 字节，本次没有扩大缓冲或增加长报文支持。请求长度继续沿用端点配置，并在手柄初始化时限制到缓冲容量。实际收到不足 8 字节或超过本次请求长度的报文会被拒绝；合法短包未收到的尾部清零，避免旧报文的尾部影响当前数据或状态过滤。解码入口也检查长度边界。

## 兼容范围

符合上述接口条件，只表示设备可以进入现有处理流程。报文字段的位置、长度、含义和取值仍须匹配；不同布局可能表现为无反应、方向错误或按键错位。

protocol `0` 本身不能证明设备是游戏手柄，其他非 Boot HID 也可能符合此接口条件。本次用于放行用户选择的同格式手柄接收器，没有通过描述符识别任意 HID 设备的用途。HID 报告布局的定义方式见 [USB-IF HID 规范](https://www.usb.org/hid)。

本次没有实现通用 HID report descriptor 解析器，没有增加 XInput 支持，也没有扩展复合设备的接口选择逻辑。不能据此承诺复合接口或不同输入报文自动兼容。平衡控制、手柄动作映射和原有轮询方式保持不变。

本次尚未烧录，原手柄回归和新手柄实测均待完成。本地编译及产物检查结果在 [开发记录](DEVELOPMENT_LOG.md) 中单独填写，不能替代手柄功能验证。

## 最小复测步骤

固定车体并让车轮离地，保持同一主板、固件和供电条件。每只手柄使用已与其配对成功的接收器。

1. **先测原手柄。** 接入原接收器，确认摇杆中位和松开按键时没有持续方向指令；依次检查摇杆四向、方向帽四向及已有动作按键，核对方向和按键含义是否与修改前一致。每次动作后回到中位或松开按键。
2. **再测新手柄。** 换用与新手柄配对的接收器，按相同顺序测试中位、四向和按键。记录无反应、方向反转、轴交换、按键错位等具体表现；不要只以“接收器被识别”作为通过依据。
3. **记录结果。** 分别记录手柄与接收器组合、所用固件提交或 HEX 摘要、上述各项表现。全部符合预期后，再单独安排落地控制验证。

## 新手柄仍无反应时

先采集以下证据，再决定是否需要扩展接口选择或增加报文适配：

- 接收器实际枚举的 VID/PID；无线手柄外壳型号不能替代接收器 USB 标识。
- 接口描述符和 HID 报告描述符，包含 class/subclass/protocol、接口序号及输入端点信息。
- 中位、单独移动各轴、方向帽和逐个按键时的原始输入报文，以及每包实际长度。

VID/PID 白名单已经取消。继续增删型号 ID 无法修正传输、接口选择或报文字段布局的问题，应先用上述证据定位差异。
