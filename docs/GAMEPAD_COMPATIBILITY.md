# USB 手柄兼容说明

固件按接收器选择报文配置：`VID=0x20BC / PID=0x5500` 使用接口 `0` 的专用 9 字节格式；其他进入现有手柄分支的设备保留 legacy 格式。USB 枚举成功只能证明接口被接入，仍须确认摇杆、方向帽和按键含义。

## 报文配置与接口选择

| 配置 | 设备和接口 | 报文约定 |
|---|---|---|
| `20BC:5500` 专用配置 | 按 VID/PID 选择，固定 USB 接口号 `0`；HID class `3`、subclass `0`、protocol `0` | 无 Report ID，实际 USB 输入恰为 9 字节 |
| legacy 配置 | 保留放宽型号白名单后的手柄入口；HID class、subclass `0`、protocol `0` | 原有 8–32 字节固定布局 |

已检查的 `20BC:5500` 接收器设备版本为 `bcdDevice=0x1003`，有三个接口。其中接口 `0`、`1` 都声明 Game Pad 集合，接口 `2` 为系统/用户控制集合。本次明确使用接口 `0`，不自动切换到接口 `1`；哪个物理手柄向哪个接口发送操作仍需用户实测。证据及精确布局见 [20BC:5500 设备记录](devices/20bc-5500.md)。

`20BC:5500` 配置跳过非 Boot 流程中的 `SET_PROTOCOL` 和启动时 `GET_REPORT`，直接通过所选接口的中断 IN 端点接收。接收缓冲为 64 字节，匹配实测端点的最大包长；解析使用实际 `XferSize`，9 字节报告不会因为端点上限为 64 字节而被当成 64 字节数据。手柄数据直接交给解析器，不再借助固定帧长 FIFO 拼接或补尾。

新配置使用端点声明的 10 ms 轮询周期（下限 1 ms）；legacy 保持原有最低 50 ms。读取手柄信息时保留最新有效帧，不因一次读取后暂时没有新包而清空。

## 20BC:5500 的字段与映射

下表的字节偏移均从实际 USB 报文的 `0` 开始。Windows HID 输入缓冲会在无 Report ID 的设备数据前补一个零字节；该占位不进入 STM32 的 USB 报文，也不能据此给所有字段增加一字节偏移。[微软 HIDP_CAPS 定义](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/ns-hidpi-_hidp_caps)

| USB 字节偏移 | 已核实字段 | 固件解释 |
|---|---|---|
| `0..1` | Button Usage `1..15`，低字节在前 | 按映射表转换到原有按键位图 |
| `2` 低四位 | Hat：`0..7` 为八方向，实测中位为 `15` | 新配置方向位：UP=`1`、RIGHT=`2`、DOWN=`4`、LEFT=`8`、中位=`0`；斜向合并相邻方向，`8..15` 按 Null 处理 |
| `3`、`4` | X、Y，8 位，逻辑范围 `0..255` | 左摇杆 X、Y |
| `5`、`6` | Z、Rz，8 位，逻辑范围 `0..255` | 右摇杆 X、Y |
| `7`、`8` | Simulation Controls Usage `C5`、`C4`，8 位 | 当前不接入控制动作 |

新配置以原始值 `128` 作为摇杆中位。X 方向使用 `raw_x - 128`，Y 方向使用 `128 - raw_y`，四轴结果均限制在 `[-127, 127]`，保证原始中位得到 `0`。X/Y/Z/Rz 是描述符字段名；将它们对应到左右物理摇杆仍需复测。

按键转换表位于 `Firmware/Hiwonder/src/gamepad_report.c`。尚未逐个采集物理按键，当前采用以下待标定映射：

| USB Button Usage | 原有动作键 |
|---|---|
| `5`、`6` | L1、R1 |
| `7`、`8` | L2、R2 |
| `9`、`10` | Select、Start |
| `11`、`12` | L3、R3 |
| `1..4`、`13..15` | 不映射 |

这只是常见 DInput 编号约定，不能作为该实物按键布局已确认的证据。暂不映射其余编号，避免未经标定的按键触发现有 PID/校准操作。后续应逐键记录 USB Usage，再调整此表；不要根据外壳印字直接猜测编号。

## legacy 配置

原有 `0x2563:0x0526/0x0575` 型号白名单已取消；其他设备进入 legacy 路径后，仍须符合原报文布局。protocol `0` 本身不能证明设备就是手柄。

| USB 字节偏移 | 保留的原有解释 |
|---|---|
| `1`、`2` | 左摇杆 X、Y，保留原有中心换算和方向 |
| `3`、`4` | 右摇杆 X、Y，保留原有中心换算和方向 |
| `5` | 方向帽，低四位取反 |
| `6`、`7` | 原有按键位图，`6` 为高字节、`7` 为低字节 |
| `20`（第 21 字节） | 报文确实包含该字节时，值为 `0x02` 继续被既有状态过滤丢弃 |

legacy 解析仍接受 8–32 字节，保持原有轴、按键和 Hat 算法；没有确认其 Hat 四向位语义与新配置相同。第 21 字节的厂商定义尚未确认，不把它解释为已经验证的无线连接状态。

## 状态与验证边界

无效报文、USB 断开及重新连接会清理手柄信息，控制层读取手柄数据时检查空指针。没有增加“长时间无新包就清零”的超时判断，因为设备可能只在状态变化时发报告。接收器仍连接而无线手柄掉线时会发什么报文尚未实测，不能据此保证识别无线失联。

调试器可观察 `gamepad_raw_buttons` 获取原始 USB Usage 位图，并通过 `gamepad_reports_accepted` / `gamepad_reports_rejected` 查看解析计数；每次重新连接时计数清零。逐键标定以原始位图为依据，不以当前暂定动作映射反推物理编号。

本次增加的是一个已取证型号的明确配置，没有实现通用 HID report descriptor 解析器，没有增加 XInput 或任意复合设备的通用接口选择能力。其他 `20BC:5500` 固件版本若改变报告格式，也需要重新验证。

解析器具备可在主机 GCC 下执行的 C 测试，供 GitHub Actions 验证字段、映射和长度边界；本次实际 C 测试、Keil 编译与产物结果见 [开发记录](DEVELOPMENT_LOG.md)。本次没有烧录，PC 上读取描述符和输入样本不等于 STM32 上已接收，也不等于完成整车验收。

## 最小复测步骤

固定车体并让车轮离地，保持同一主板、固件和供电条件。每只手柄使用已与其配对成功的接收器。

1. **原手柄回归。** 检查中位、左右摇杆四向、方向帽和原有按键；每次动作后回中或松开。确认 legacy 的方向、中心和动作保持原行为。
2. **20BC:5500 接口 0。** 确认新手柄操作产生接口 `0` 报告，再检查四轴中位、四向和方向帽八向。若接口 `0` 没有随操作变化，应先查接口 `1` 是否对应当前手柄，不在运行中自行切换接口。
3. **逐键标定。** 一次只按一个键，记录物理按键、USB Usage、固件动作。重点核对待确认的 Usage `5..12`；确认 `1..4/13..15` 不触发现有控制动作。
4. **状态复测。** 在有方向输入后松开，再检查 USB 拔出、重插后的控制量清理；另行记录无线关机/失联时接收器行为，不把 USB 拔出结果代替无线失联测试。
5. **保存证据。** 记录固件提交或 HEX 摘要、接收器版本、接口和各项结果。上述项目符合预期后，再单独安排落地控制验证。

若无反应或字段异常，先取得实际 VID/PID、接口/报告描述符以及中位、单轴、逐键输入的原始报文和长度，与设备记录比较。修改型号 ID 无法修正接口或报文布局差异。
